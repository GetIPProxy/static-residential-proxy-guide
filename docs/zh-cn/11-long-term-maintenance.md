# 静态住宅 IP 买到之后：建立基线、环境一致性检查、定期复检与故障排查

> **适合谁读**：已经买到静态住宅 IP 的所有人，尤其是每天使用它的运营人员和助理
> **读完你能**：存下刚拿到 IP 时的第一份检测记录，按清单检查接入和复检，出了问题能分清该查线路、出口 IP 还是账号
> **阅读时间**：约 16 分钟
> **系列位置**：第 11 篇 · 出口

---

## 先说结论

- **刚拿到 IP，先查一遍，把结果和日期存下来。** 这份记录就是「基线」。以后出了问题，用同样的方法再查一次，看看是地址换了，还是报告里某一项变了。
- **接入后检查实际走的出口**。确认应用是否用了你配置的代理，再按清单检查 DNS、WebRTC、IPv6 以及设备的时区和语言设置。
- **检测结果会变**：每月例行复检一次，重要操作前和出现异常时额外复检。
- **出了问题，先看代理能不能连上。** 接下来按顺序查线路、IP 的检测结果、环境泄露和账号状态。查到原因后，再决定要不要换 IP。
- **到期前先问清楚续费能不能留住原 IP。** 按卖家的条款设好提醒。

## 一、到手第一天：建立"出生证明"基线

### 为什么要建立基线

数据库更新后，同一个 IP 也可能被重新分类，风险分也可能变。把刚拿到手时的结果存好，以后遇到问题，就能拿它对照下面几项。

- 是出口 IP 换了，还是同一个 IP 的报告变了？
- 是这个 IP 的问题，还是账号或环境的问题？
- 和供应商沟通时，拿什么作为依据？

### 怎么建立

1. **确认出口**：用 ifconfig.me、IP.SB 等站点确认当前出口就是你买的 IP，同时确认 IPv6 没有绕过代理（见第二部分）；
2. **多平台检测**：按[第 04 篇](04-ip-checker-platforms.md)的方法，至少检测以下内容：
   - 用 ping0 查 IP 类型、风控值、原生 / 广播、共享人数，以及自治系统编号（ASN）、企业和注册地的历史记录；
   - 用 IPQS 查欺诈分（`fraud_score`）、`proxy`、`recent_abuse` 和 `connection_type`；
   - 想再查风险分就用 Scamalytics，想核对网络和地区就用 ipinfo；
   - 至少 3 个地理库的国家 / 城市；
3. **目标平台校验**：在不登录业务账号的前提下，看目标平台显示的地区；
4. **性能测试**：延迟、下载与上传速度；需要直播的，测试长时间推流的稳定性；
5. **截图存档**：每张截图都要能看到检测日期，按 IP 归档；
6. **填写记录表**：按[第 04 篇](04-ip-checker-platforms.md)的检测记录表填写，并设定下次复检日期。

到手查出来和下单前说好的不一样，就把截图发给卖家（[第 03 篇](03-proxy-ip-labels.md)）。趁业务还没接上这个 IP，先问能不能按约定换。

## 二、上号前：环境一致性检查

一个纯净的 IP，如果你的真实信息从别的渠道"漏"了出去，平台看到的就不只是这个 IP。

### 1. 四种常见泄露

| 泄露类型 | 是什么 | 打个比方 | 怎么检查 |
|---|---|---|---|
| DNS 泄露 | 你访问网站时的域名解析请求没有经过代理，而是走了本地网络的 DNS 服务器 | 寄信用的是新地址，但查地址簿时打的还是老家的电话 | ipleak.net 的 DNS 部分、BrowserLeaks 的 DNS 页面 |
| WebRTC 泄露 | 浏览器的 WebRTC 功能（用于音视频通话）可能绕过代理，暴露你本地的真实 IP | 门口挂了新门牌，但窗户上还贴着老地址 | BrowserLeaks 的 WebRTC 页面、ipleak.net |
| IPv6 绕过 | 代理只处理 IPv4，而你的网络同时有 IPv6，部分流量直接通过 IPv6 发出 | 前门走了代理，后门还开着 | IP.SB、ipleak.net（同时显示 IPv4 和 IPv6） |
| 部分应用不走代理 | 只给浏览器配置了代理，其他应用或手机 App 仍在使用本地网络 | 只有一个房间换了门牌 | 在对应的应用里访问 IP 查询页面 |

**判断标准**：所有检测页面上显示的 IP，都应该是你买的那个 IP；DNS 服务器的位置应该与 IP 所在地区一致，或至少不应该是你本地运营商的 DNS。

### 2. 时区、语言与地区设置

| 检查项 | 应该是什么样 |
|---|---|
| 系统时区 | 与 IP 所在地区一致 |
| 浏览器语言 | 符合目标市场用户的习惯 |
| 系统语言与地区格式 | 与账号的定位相符，不出现明显矛盾 |

时区相差十几个小时，是环境不一致最典型的信号之一。IPQS、ipinfo 等平台都会给出 IP 对应的时区，可以直接对照。

### 3. 常用的环境检测工具

| 工具 | 主要检查什么 |
|---|---|
| BrowserLeaks | 按类别逐项展示浏览器信息：IP、WebRTC、DNS、Canvas 等指纹，只给原始数据，不打分 |
| ipleak.net | 一个页面同时检查 IP、WebRTC 和 DNS，显示 IPv4 与 IPv6 |
| ping0 环境检测 / IP Leak 检测 | 中文用户常用的环境检测页面 |

**用法建议**：先查 IP 和 DNS，再查 WebRTC，最后查指纹。两个工具都显示同一个泄露，说明泄露是真实的。

### 4. 上号前检查清单

- [ ] 出口 IP 是买的那个 IP（IPv4）
- [ ] 没有 IPv6 绕过代理
- [ ] 没有 WebRTC 泄露
- [ ] DNS 不是本地运营商的服务器
- [ ] 系统时区与 IP 地区一致
- [ ] 浏览器语言符合目标市场
- [ ] 手机和电脑（如果都要登录）都通过同一个 IP
- [ ] 每个需要独立的账号，使用独立的浏览器环境

## 三、接入方式：HTTP(S) 还是 SOCKS5

静态住宅 IP 通常同时支持 HTTP(S) 和 SOCKS5 两种协议。

| | HTTP(S) 代理 | SOCKS5 代理 |
|---|---|---|
| 适用范围 | 主要用于网页访问 | 更通用，可以转发各类 TCP 流量；部分实现支持 UDP |
| 配置难度 | 浏览器、大多数工具都原生支持 | 大多数代理客户端和指纹浏览器都支持 |
| 适合 | 只在浏览器里使用的场景 | 需要在多种应用中使用、或需要音视频的场景 |

**一个容易忽视的细节：DNS 在哪里解析**

使用 SOCKS5 时，域名可以在本地解析，也可以交给代理服务器解析。如果在本地解析，就可能发生 DNS 泄露。以 `curl` 为例：

```bash
# 在本地解析域名（可能泄露 DNS）
curl --proxy "socks5://用户名:密码@代理地址:端口" https://ipinfo.io/json

# 交给代理解析域名（推荐）
curl --proxy "socks5h://用户名:密码@代理地址:端口" https://ipinfo.io/json
```

在浏览器和代理客户端里，对应的设置通常叫"通过代理进行 DNS 解析"或"远程 DNS"，建议开启。

**关于 UDP**：直播推流、部分音视频通话会用到 UDP。如果你的业务需要，确认供应商和你使用的客户端都支持 UDP 转发，并实际测试。

### 多设备接入

| 设备 | 常见做法 | 注意事项 |
|---|---|---|
| 电脑浏览器 | 在浏览器或代理扩展中配置 | 只对浏览器生效 |
| 指纹浏览器 | 为每个浏览器环境单独配置一个代理 | 一个环境对应一个 IP，不要混用 |
| 手机 | 使用支持 HTTP(S) / SOCKS5 的代理客户端 | 确认 App 的流量确实经过代理 |
| 路由器 | 在支持代理的路由器上配置，让整个局域网走同一个出口 | 局域网内所有设备都会共用这个 IP |

**最常见的错误**：电脑走静态 IP，手机却用本地网络登录同一个账号。对平台来说，这个账号就同时出现在了两个地方。

## 四、从中国大陆连接：直连还是中转

中国大陆的用户连接海外静态住宅 IP 时，经常遇到延迟高、丢包、断线等问题。原因通常不在 IP 本身，而在**跨境网络链路**。

| 方式 | 怎么做 | 优点 | 风险 |
|---|---|---|---|
| 直连 | 本地设备直接连接海外的静态住宅 IP | 配置简单，少一层环节 | 受跨境链路质量影响，高峰时段可能不稳定 |
| 中转（链式代理） | 先连接一个线路较好的中转节点，再由中转节点连接静态住宅 IP | 连接更稳定 | 多一层故障点；中转节点配置不当可能造成泄露 |

**使用中转时要确认**：最终出口仍然是静态住宅 IP（用 ifconfig.me 等站点检查），而不是中转节点的 IP。

**怎么判断问题出在中转还是 IP**：
- 直接从中转节点所在的服务器测试静态住宅 IP 的连通性；
- 如果从中转节点访问正常、从本地访问不正常，问题在本地到中转节点这一段；
- 如果从中转节点访问也不正常，问题在静态住宅 IP 或其所在网络。

## 五、定期复检

### 复检节奏

| 时机 | 检查什么 |
|---|---|
| 每月例行 | 用同样的平台和方法再查一遍，对照上次的记录 |
| 重要操作前（如大促、新账号上线、店铺资料变更） | 风险信息、连通性、目标平台显示的地区 |
| 出现异常时 | 按第七部分的排查顺序检查 |
| 续费前 | 确认 IP 状态仍然符合要求，再决定是否续费 |

### 看到变化时怎么办

| 发生变化的维度 | 常见原因 | 怎么处理 |
|---|---|---|
| 风险分小幅波动（仍在绿灯区间） | 数据库可能更新了 | 记下这次结果，下次用同样的方法复检 |
| 单个平台的分数明显上升 | 检测站可能更新了数据，查询方式也可能不同 | 先用原来的方法再查一次，再换个来源核对。按买时约定的标准处理 |
| 查到近期滥用（如 IPQS `recent_abuse=true`） | 报告里新增了这个 IP 的近期滥用记录 | 把结果发给卖家核实。对照第八部分，再决定要不要换 |
| 报告显示的城市变了 | 数据库更新，或运营商更新了地区信息 | 先确认还是同一个出口 IP，再看实际使用的平台显示的地区有没有变 |
| IP 类型从住宅变为机房 | 数据库重新分类 | 看多数平台的结论；如果多数平台都变了，联系供应商 |
| ASN 或企业记录变了 | 宣告网段的网络换了，或企业改名 | 先看「首次出现」时间，再查变的是名称还是宣告这个网段的 ASN（[第 08 篇](08-asn-and-isp.md)） |
| 「共享人数」升了一档 | ping0 估算关联到的用户变多了 | 把前后两次的结果发给卖家，请它确认有没有把这个 IP 分给其他客户 |

## 六、续费管理

静态住宅 IP 通常按周期计费。到期前先看购买条款，确认续费能不能留住原 IP。要是过期后卖家收回了地址，再买可能会分到新的 IP。

原 IP 被收回后，下次登录可能就得用另一个出口。平时可以这样管续费。

- 按[第 10 篇](10-scenarios-regions-teams.md)的台账说明，记下每个 IP 的到期日期；
- 提前一周左右设置提醒，不要卡在最后一天；
- 多个 IP 统一管理，批量续费；
- 续费前做一次复检，确认 IP 仍然符合要求。

## 七、出了问题：按顺序排查

账号或业务出了问题，先看代理能不能连上，再测线路稳不稳。已经在用的 IP，查完下面几项，再决定要不要换。

### 排查顺序

| 步骤 | 检查什么 | 怎么检查 | 如果有问题 |
|---|---|---|---|
| 1. 连通性 | 代理能不能连上？ | 用 ifconfig.me 等站点测试；检查账号密码、端口、协议是否正确 | 检查配置；联系供应商排查交付或认证问题 |
| 2. 线路 | 连接是否稳定？延迟和丢包是否正常？ | 不同时段测试；如果使用中转，按第四部分分段测试 | 调整线路或中转节点 |
| 3. IP 质量 | 地址换了，还是报告里的结果变了？ | 用相同的平台和方法复检，对照刚拿到时存下的记录 | 按第五部分的表格处理 |
| 4. 环境泄露 | 有没有 DNS、WebRTC、IPv6 泄露？时区语言是否一致？ | 按第二部分的清单逐项检查 | 修复泄露和设置 |
| 5. 账号自身 | 是否有资料变更、异常操作、内容违规、支付问题？ | 查看平台的通知、账户状态和登录记录 | 按平台的流程处理，必要时申诉 |

### 常见症状速查

| 症状 | 最可能的原因 | 先查什么 |
|---|---|---|
| 完全连不上 | 配置错误、代理到期、认证失败 | 第 1 步：连通性 |
| 时好时坏、高峰期卡顿 | 跨境链路或中转节点不稳定 | 第 2 步：线路 |
| 能连上，但目标网站显示的地区不对 | 数据库定位差异、泄露 | 第 4 步：环境泄露；第 3 步：地理复检 |
| 平台频繁要求验证 | 环境变化、泄露、账号行为异常 | 第 4 步、第 5 步，再看第 3 步 |
| 上传视频很慢、直播卡顿 | 上行带宽不足、不支持 UDP | 第 2 步：线路与性能测试 |
| 账号受限、店铺被审核 | 多为账号、资料、支付或行为原因 | 第 5 步：账号自身 |

把排查过程和截图记录下来。如果最终需要联系供应商，提供订单号、使用的客户端和协议、错误信息、测试时间，可以大大加快排查速度。

## 八、什么时候该换 IP，什么时候不该换

| 该换 | 不该换 |
|---|---|
| 出现近期滥用记录，且多个来源都显示高风险 | 单个平台的分数小幅波动 |
| 多数平台都把它识别为机房，与购买时的约定不符 | 只有一个平台的类型结论和其他平台不同 |
| 目标平台显示的地区持续不符合业务需求 | 账号出现异常，但还没有排查环境和账号自身 |
| 买的是独享，确认卖家又把同一个 IP 分给了其他客户 | 只是想"找一个更干净的" |
| 长期无法稳定连接，排除了线路原因 | 一次性的连接中断 |

换 IP 会让账号的登录出口变一次。确认需要换之后，按业务原来的地区和网络类型要求选，再记下新地址和检测日期。

## 九、按人群的运维重点

| 人群 | 运维重点 |
|---|---|
| A 海外社媒账号长期运营者 | 手机和电脑使用同一出口；直播前测试上行与稳定性；不频繁换 IP |
| B 跨境电商店铺运营者 | 大促前复检；助理接入走同一出口；续费提前管理 |
| D 广告账户运营与投放团队 | 团队统一出口；账户异常时先查账户本身 |
| C 面向特定城市的本地业务运营者 | 定期查看目标平台显示的地区 |
| E 代运营机构、海外虚拟助理团队 | 台账维护、批量续费、人员变动时收回权限 |
| F 固定地区的长期功能验证人员 | 每次测试记下出口 IP 和报告显示的城市。结果变了，先对照两次记录 |

## 常见问题

**Q：检测平台显示的地区和我买的不一样，是 IP 有问题吗？**
先确认出口是否正确、有没有泄露。然后看多个地理库的多数结论和目标平台显示的地区。单个平台不一致很常见（[第 04 篇](04-ip-checker-platforms.md)）。

**Q：我已经配置了代理，为什么检测页面还是显示我的本地 IP？**
最常见的原因是 WebRTC 泄露、IPv6 绕过，或者这个应用没有走代理。按第二部分的清单逐项检查。

**Q：多久复检一次比较合适？**
建议每月复检一次。遇到大促等重要操作，或使用中出了异常，再额外查一次。用同样的平台和查询方式，结果才好对照。

**Q：到期忘了续费，还能拿回原来的 IP 吗？**
先问卖家原 IP 还在不在。如果已经收回，重新买时可能会分到新地址。以后可以按到期日期提前设个提醒。

**Q：账号被限制了，要不要马上换 IP？**
先看平台的通知和账户状态，再按第七部分核对连接和出口。要是平台要求验证或申诉，按它的流程处理。
